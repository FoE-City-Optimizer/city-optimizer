## Practical boundary

The M2 oracle and CP-SAT spike need a defined **test model**, not a finalized game adapter. Treat available cells, fixed rectangles, road cells, root, demand and objective as explicit test-case inputs. An independently checked optimal answer under that model is meaningful evidence about the algorithm. It is not evidence that the source replay has the same semantics or that a proposed real-city rearrangement is valid.

The scheduled [city-viewer prototype #40](https://github.com/FoE-City-Optimizer/city-optimizer/issues/40) belongs under #2 because it exercises acquisition and exposes real geometry and statistics. It can render the reviewed replay now, then test a bounded temporary Chrome observation. It must show omissions and stale/partial state, collect only the minimum city fields, avoid game actions and uploads, and undergo privacy review before a live installation. It need not be retained as production code.

```text
Synthetic model + oracle + CP-SAT experiment (M2 #4) ── starts now
Reviewed #24 replay → viewer prototype (M1 #2) ──────── starts now
Live viewer design → privacy review → owner live check ─── parallel M1 evidence
Source semantics + eligibility + Snapshot v1 ─────────── required for real-city solver claims
```

M1 closes when its Epics meet their stated exit criteria or the owner explicitly revises them. M2 can proceed in parallel. The next planning check should use executable prototype and solver results to decide which source questions actually block the first usable plan; it should not require exhaustive knowledge of every game mechanic.

## Decisions, verification and handoff

Accepted [ADR-004](../adr/004-cp-sat-spike.md) permits a feasibility spike, [ADR-005](../adr/005-snapshot.md) requires a project-owned validated wire snapshot for later boundaries, [ADR-006](../adr/006-read-only.md) limits integration to read-only data, and [ADR-010](../adr/010-objectives.md) orders validity before road minimization. ADR-011 and ADR-016 remain Proposed. The viewer prototype and algorithm spike do not accept them by implication.

Verification now: the solver spike needs oracle agreement, independently checked layouts, and honest proof/status on tiny positive and negative cases. The viewer needs a repeated #24 replay, counts and geometry consistent with that reviewed artifact, clear missing-data diagnostics, and a bounded live-result report if installed. A new real-city fixture or changed bytes require exact-artifact privacy review. No raw responses, credentials, session tokens, social data or full-session dumps may be stored; no gameplay is automated.

**Handoff:** #40 is a native child of #2 and M2 [#4](https://github.com/FoE-City-Optimizer/city-optimizer/issues/4) has the explicitly synthetic first phase; both are Ready in Project #1. Backlog Refinement can refine the next small implementation queue; Research and Security & Privacy review the live viewer design; Architecture & Planning revisits the model after the first executable results. No due date is inferred.
