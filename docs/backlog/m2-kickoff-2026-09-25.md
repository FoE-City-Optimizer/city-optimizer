# M2 kickoff — solver foundation with a visible city prototype

**Decision, 2026-09-25:** Start bounded M2 work while M1's production-grade data and contract outcomes remain open. The M1 reports give enough evidence to choose a deliberately small **experimental grid model** and test solver behavior. They do not establish that a solution for the reviewed real city is game-valid. Keep those two claims separate.

## What starts now

1. **Solver feasibility under [M2 #4](https://github.com/FoE-City-Optimizer/city-optimizer/issues/4):** implement a tiny exhaustive oracle and a CP-SAT comparison on manually authored, clearly synthetic grid cases. Start with available cells, fixed rectangular buildings, one fixed Town Hall, orthogonal 1×1 road cells, collision rules, and explicit `NONE`/`SINGLE` road demand supplied by the test case. Compare road count and proof/status with the oracle. Include disconnected, overlap, impossible and timeout cases. Publish code and a reproducible benchmark report. These are valid results _for the stated experimental model_, not proof of current FoE mechanics or a production engine choice.
2. **Disposable [city-viewer prototype #40](https://github.com/FoE-City-Optimizer/city-optimizer/issues/40) under [M1 acquisition Epic #2](https://github.com/FoE-City-Optimizer/city-optimizer/issues/2):** reuse the reviewed [#24 replay](../research/issue-24-real-city-fixture.md) for an immediately visible city map and statistics. In a temporary Google Chrome extension on the authorized world, passively observe only selected startup and change fields and render the geometry that is explicitly known. Show missing coordinates, unresolved footprints, special-class counts, and stale/incomplete state rather than filling defaults. A subsequent owner-operated live check tests whether the prototype updates after a change. The prototype may be discarded; it is not the production collector, Snapshot v1, or a solver-valid city.

These workstreams run in parallel. The viewer gives a tangible representation and exposes data gaps. The solver spike tests the mathematical model. Neither waits for the other, and neither silently promotes source assumptions into accepted game rules.

The [charter](../project/project-charter.md) and accepted [ADR-004](../adr/004-cp-sat-spike.md), [ADR-005](../adr/005-snapshot.md), [ADR-006](../adr/006-read-only.md), and [ADR-010](../adr/010-objectives.md) still govern the project. M2 may use an internal experiment input; it must not call that input Canonical City Snapshot v1. `packages/domain` owns later accepted domain rules, `packages/contracts` owns the later wire contract, and the solver worker never reads the game session. No production boundary moves through this plan.

## Delivery sequence and checks

```text
Ready now: explicit synthetic cases → exhaustive oracle → CP-SAT formulations
                                      ↓
                              independent checks + benchmark report

Ready prototype: reviewed #24 replay → local map/stats
                 bounded Chrome design + privacy review → owner-installed temporary live viewer
                                                     ↓
                                        observed gaps and update behavior

M1 source/contract evidence → eligible real-city compiler → real-city M2 validation
```

The first useful review is a running oracle/CP-SAT comparison on a few tiny cases and a fixture map with honest unknown counts. The benchmark must report inputs, objective, time limit, memory, road count, proof status and any disagreement. The viewer must show whether its map came from replay or live observation, whether it is partial/stale, and which shapes lack explicit positions or footprints. No optimality or fully valid city claim is allowed from the viewer.
