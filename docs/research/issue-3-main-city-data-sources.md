# Issue #3 — read-only main-city data sources

**Status:** live startup, static metadata, and one reversible change observed
**Observed:** 2026-09-23, approximately 15:37–16:03 UTC
**Scope:** [issue #3](https://github.com/FoE-City-Optimizer/city-optimizer/issues/3). [#23](https://github.com/FoE-City-Optimizer/city-optimizer/issues/23) owns passive browser-observation feasibility and [#24](https://github.com/FoE-City-Optimizer/city-optimizer/issues/24) owns sanitized fixture capture. This is evidence for those tasks, not a snapshot contract or collector implementation.

## Method and boundaries

The owner signed in personally and opened the main city in connected Chrome. After the owner enabled and approved Chrome Developer mode access, I observed a reload through a temporary response-stage filter limited to `https://pl4.forgeofempires.com/game/json` XHR/fetch responses. The filter briefly paused matching responses, parsed selected city fields in memory, and continued the original responses unchanged. I then read only game-supplied static metadata resources needed to join placed entity keys to geometry and street requirements. For the update check, the owner manually moved one road tile and moved it back while I passively read the matching game response bodies. I did not perform gameplay actions, save a raw response, export a HAR, inspect headers or request bodies, or collect cookies, credentials, tokens, chat, social, or unrelated account values. Network observation was stopped and temporary in-memory city data was discarded after the check.

The response-stage filter briefly held a loading response at 55% while waiting for inspection. I released it and cleared the filter; the game rendered normally afterward. The manual move used passive `Network` observation, with no response interception. A future observer must avoid pausing ordinary game loading.

The main city was visually confirmed. It rendered in a canvas, so DOM text did not provide a field-level source. The loaded asset name `merged-game-c3b9b79d.js` is a revalidation fingerprint, **not** a confirmed game build. The game build and Chrome version remain unknown. The authorized city was not confirmed to be a designated test city.

The `/game/json` startup response mixed multiple unrelated service entries and was approximately 3 MB. Only `StartupService.getData.responseData.city_map` and the descriptor list in `StaticDataService.getMetadata.responseData` were examined for this research. Selected static resources came from game-supplied CDN URLs at `/start/metadata`, with an `id` query parameter; no query value is retained here. These observations cover one city, one world, and one game asset fingerprint.

## Geometry cross-check and counterexamples

For this city, interpreting omitted `x`/`y` as zero and joining the two footprint formats placed the 398 ordinary on-grid entries (`generic_building`, `greatbuilding`, `street`, `main_building`, `military`) in 3,954 distinct cells, all inside the 3,968 unlocked cells and with no overlap. Fourteen unlocked cells remained free. Swapping width and length created 539 overlap cells and 27 cells outside the unlocked mask. This strongly supports the x/y orientation and zero-default hypothesis for this sample. It does **not** prove the serialization default; verify that rule from an independent client/schema source or another controlled fixture before silently substituting zero.

Absence cases matter: a generic definition has no top-level `width`/`length`; 72 generic keys have no street requirement component; 21 placed entities omit one coordinate; 21 unlocked rectangles omit one coordinate; 14 blocked positions omit at least one coordinate. A field's absence needs its verified schema rule, not a generic truthiness check. Blocked positions did not reduce this city's unlocked mask, so their meaning remains open.

In the first `moveEntities` response, `connected` appeared on one of 25 entries; in the reversal response it appeared on all 25. `state` appeared throughout. Neither field was needed to identify the moved road or update its position, and their values were not retained. The response was accompanied by other game services, reinforcing the need to select the `CityMapService.moveEntities` entry and project only relevant fields. One move and reversal do not establish behavior for adding, deleting, selling, expanding, or changing building levels.

| Temporary instance join key; static entity key; eligible type; grid coordinates; footprint; verified street requirement; unlocked cells; relevant blocked cells; Town Hall discriminator; current street positions | Display name, art asset, production, resale and resource costs, ranking, boosts/bonuses, construction and entity state, `connected` as a requirement proxy, metadata for unplaced entities | `player_id`, player/world identity, cookies, credentials, session tokens, authentication headers, chat, friends/guild data, unrelated account or social fields, full request/response archives, full-session network dumps |

The lookup had 2,858 descriptors; the top-level metadata list had 41. A minimal adapter can select descriptors for keys present in the city and project only needed fields. Neither whole list belongs in a city snapshot. The startup response also mixes city data with unrelated services, so filtering must occur before a snapshot crosses the extension boundary.

## Recommendation and open evidence

Recommend a read-only, source-allowlisted adapter that extracts `city_map` from `StartupService.getData`, resolves placed `cityentity_id` through `building_entity_lookup`, and projects only verified footprint/street fields from the two observed formats. For the observed move event, merge the selected `moveEntities` entity subset by `id` and revalidate geometry; do not replace the whole city with those 25 entries or assume each returned entry changed position. Validate key uniqueness, geometry, a source version/fingerprint, and required fields; fail visibly on unknown critical variants. Keep the canonical snapshot independent of external paths, per [ADR-005](../adr/005-snapshot.md), and keep collection minimal and read-only, per [ADR-006](../adr/006-read-only.md). This is a research recommendation, not a schema decision.

Still to verify: update coverage for actions other than moving a road and for other city contexts; instance-key stability beyond the observed move; coordinate omission semantics; missing street requirement semantics; blocked-area meaning; handling of special, linked, chain, and set buildings; game build and browser version; another city/world/schema variant. [ADR-011](../adr/011-special-buildings.md) is proposed, not accepted. Hand gaps to Architecture & Planning and Backlog Refinement; use #23 for a safe passive observer and #24 for a sanitized repeatable fixture. Do not label a geometric layout functionally valid or optimal based on this check.
