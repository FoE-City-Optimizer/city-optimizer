# Issue #23 — passive browser observation boundary

**Status:** Chrome document-start and message-boundary proof completed with a disposable probe; Firefox live verification blocked by available computer-use tooling; cross-browser and update completeness remain open.
**Research date:** 2026-09-25 UTC.
**Scope:** [Issue #23](https://github.com/FoE-City-Optimizer/city-optimizer/issues/23), following [Issue #3's merged report](issue-3-main-city-data-sources.md) and [PR #28](https://github.com/FoE-City-Optimizer/city-optimizer/pull/28). This is evidence for a later browser collection decision, not a collector implementation or an accepted ADR.

## Concise answer and confidence

A read-only Chrome observer has a demonstrated narrow path: in the authorized main city, a disposable MV3 extension installed `MAIN` and `ISOLATED` scripts at `document_start`, observed `/game/json` XHR startup service markers, and passed only bounded boolean diagnostics through the isolated bridge to the runtime. Both scripts reported `document.readyState === "loading"` on one reload. The earlier #3 session established that selected startup and one move response contain needed city facts. **This does not prove complete update coverage, authenticity against hostile page scripts, or production readiness. Firefox remains untested in a live city.** Confidence is **high** for the one Chrome startup and boundary observation, **medium** for the candidate mechanism beyond that reload, and **low** for complete cross-browser feasibility. Issue #23's exit evidence is therefore incomplete.

## Method and concrete observations

1. Read #23 through `gh issue view 23`, its predecessor #3, merged PR #28, the relevant M1 plan, charter sections 10 and 24, accepted ADR-005/006, proposed ADR-013, privacy and component-boundary notes, and the extension shell. No production collector, manifest, or fixture exists in `apps/extension`.
2. Reused the owner's authorized Chrome main-city session after the owner selected their existing world. The live page was `https://pl4.forgeofempires.com/game/index?ref=dotcom`. The installed Chrome binary was `154.0.8037.58` (file version). The page loaded `merged-game-c3b9b79d.js`, the same asset fingerprint as #3; it is **not** a verified game build number.
3. Enabled CDP `Network` metadata for that tab, reloaded the game, and filtered event output to the origin and pathname of `/game/json`. The buffered events included multiple HTTP 200 `application/json` responses classified by Chrome as `XHR`. The event buffer reported `truncated: true`, so response counts and startup completeness cannot be inferred. No headers, request bodies, URL query values, HAR, or full-session archive were recorded.
4. During an owner-performed road move/reversal window, additional HTTP 200 `/game/json` responses classified as `XHR` were observed. Request timing alone does not identify the service or prove which response corresponds to each move. The #3 report independently observed `CityMapService.moveEntities` and a 25-entity partial refresh for one earlier move/reversal.
5. The connected CDP surface rejected `Page.addScriptToEvaluateOnNewDocument`; hence this method could not test early MAIN-world injection. A subsequent local approval review rejected `Network.getResponseBody` for the live change response because it retrieves the entire private response before filtering. No further response-body access was attempted. The response-stage filter used in #3 is not a production-safe observer: it once held loading at 55% until released.
6. After the owner manually loaded the [disposable probe](issue-23-chrome-probe/README.md), a reload of the same Chrome tab produced `bridgeReadyState: "loading"`, `mainReadyState: "loading"`, `accepted: 2`, `rejected: 4`, `runtimeAccepted: 2`, `runtimeRejected: 1`, `startup: true`, `metadata: true`, `xhr: true`, `fetch: false`, and `move: false`. The first accepted event was the MAIN init marker; the second was a selected `/game/json` XHR source marker. A rendered main-city screenshot confirmed that the page loaded with the probe active; the screenshot was not saved because it contained unrelated account/social content. The diagnostic is a page-visible DOM attribute and can be forged by page code, so it is evidence of this controlled run, not an authentication mechanism.
7. Firefox `156.0.1` is installed locally (binary file version). The owner opened an authorized Forge of Empires Firefox window for this research. The available Windows computer-use tool stopped before reading it because browser URL policy enforcement is not supported for that Firefox surface. No Firefox page, request, payload, or extension behavior was inspected. This is a **verification-tool blocker**, not evidence that Firefox cannot support a collector.
8. The owner removed the temporary extension and reloaded the game. The `data-foe23-probe` attribute was then absent from the same tab. This verifies the diagnostic no longer ran on that reload; it does not independently audit Chrome's installed-extension list.

The previous #3 observation remains the only field-level live evidence: `StartupService.getData.responseData.city_map`, `StaticDataService.getMetadata` and selected `/start/metadata` definitions supplied placed entities, geometry, roads, Town Hall, footprints, and street requirements; one `CityMapService.moveEntities` response supplied a partial refresh. The startup response mixed unrelated services and was about 3 MB. These paths must be selected and minimized before any message leaves MAIN. See the #3 report for exact paths, counts, absence cases, and limits.

## Threat boundary and minimum-permission hypothesis

The game page and every raw response are untrusted. MAIN-world code is page-visible and page-modifiable; it must contain no secrets, privileged commands, or backend credentials. A page can forge messages even when `event.source === window` and `event.origin` matches the page, because legitimate and hostile page scripts share that origin. Origin/source checks are necessary routing checks, **not authentication of city facts**. The isolated bridge should accept only a fixed message type, exact expected origin/source/frame, allowlisted field shape, bounded byte length and counts, and explicit source state; the runtime should re-check sender tab/origin/frame and validate again. No raw response object, arbitrary URL, page-supplied command, headers, tokens, or unrelated service entry should cross the bridge. The API still treats a canonical snapshot as untrusted per ADR-005.

For a static `document_start` approach, the first permission experiment should use the exact authorized game-world HTTPS host and top frame, with no `webRequest`, `debugger`, `cookies`, `<all_urls>`, or broad CDN host access unless a concrete source gap proves a need. This is a **project recommendation**, not a settled manifest. Static metadata is currently fetched from a game-supplied CDN URL after descriptor resolution; the extension's need for CDN host permission versus page-context observation has not been tested. Multi-world permission scope and user consent need a separate choice before production.

- #23 is open and asks for a versioned browser matrix, observed startup/update coverage, threat boundary, minimum permissions, failures, alternatives, and an ADR-006/013 recommendation.
- The current connected Chrome main-city page used the asset fingerprint above; its observed `/game/json` responses were XHR, HTTP 200, JSON. Event-buffer truncation prevents a completeness claim.
- On one Chrome reload, both probe scripts reported `loading`; the bridge accepted two bounded messages and rejected four malformed/wrong-source examples, while the runtime accepted two and rejected one invalid internal message. The accepted source marker reported XHR startup city map and metadata entries. The game rendered with the probe active, and the diagnostic disappeared after owner removal and reload.
- #3's 2026-09-23 authorized Chrome check mapped selected startup and one move response, but was one world, one city, one asset fingerprint, and no verified browser or game build version.
- The extension package is currently a TypeScript shell with no collector or manifest.

### External claims, current documentation reviewed 2026-09-25

- Chrome's [content-script documentation](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts) defines static matching, `world`, `document_start`, isolation, and page messaging. It describes API capability, not behavior in this game.
- Mozilla's [content-script manifest reference](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/content_scripts) and [Firefox 128 release notes](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/128) establish Firefox MAIN support and document-start semantics. They do not prove compatibility in Firefox 156 with this page.
- Chrome's [`webRequest` reference](https://developer.chrome.com/docs/extensions/reference/api/webRequest) and [DNR reference](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest) expose lifecycle/header/rule features, with no documented API for projecting response JSON fields. Mozilla's [`filterResponseData`](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/webRequest/filterResponseData) documents stream-control permissions and the need to write/close/disconnect to avoid holding responses.
- Mozilla's [cross-browser background reference](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background) documents Chrome service workers versus Firefox background scripts/event pages. The [Chrome `activeTab` reference](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab) defines user-invoked temporary access.
- The [Chrome Web Store minimum-permission guidance](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq), [Chrome disclosure policy](https://developer.chrome.com/docs/webstore/program-policies/disclosure-requirements), [Mozilla add-on policies](https://extensionworkshop.com/documentation/publish/add-on-policies/), and [Firefox built-in consent guide](https://extensionworkshop.com/documentation/develop/firefox-builtin-data-consent/) govern eventual distribution. Policy compliance has not been reviewed by either store.

### Inferences

- A static, narrowly matched document-start MAIN script has demonstrated startup visibility on one reload. A click-triggered `activeTab` injection after loading would miss earlier startup unless the user deliberately reloads after registration.
- The current `/game/json` XHR path makes an XHR observer more immediately relevant than a fetch-only observer. It does not make fetch coverage unnecessary for future variants.
- A content-script bridge can reduce the data that reaches the privileged runtime, but it cannot authenticate a city merely because the message has the page's origin. Every downstream boundary must validate.

### Project recommendations, not accepted decisions

- Use the completed disposable Chrome probe as narrow feasibility evidence. A production design still needs exact-field projection, schema-version handling, source-loss detection, and a threat model for schema-valid page forgery. If Firefox remains in scope, repeat the live boundary experiment through an approved Firefox inspection path. Keep all raw payloads ephemeral and do not use response-blocking filters for the default path.
- Treat startup and update completeness as explicit adapter states. A missed startup, unknown service variant, failed metadata join, or lost update requires a visible rescan/error; never substitute defaults or call a partial city complete.
- Architecture & Planning should use the Chrome bridge evidence and browser matrix to refine ADR-006 and proposed ADR-013 while deciding the Firefox scope. Security & Privacy should review the chosen production permission and trust boundary before collector implementation.

## Security & Privacy review of the disposable Chrome probe

The [probe source](issue-23-chrome-probe/README.md) is marked experimental and limited by its manifest to `https://pl4.forgeofempires.com/game/*`. It requests no privileged extension API or background host permissions, though the static content-script match grants access to that exact page. MAIN code has no extension API access or secret. It reads only the `/game/json` XHR response in page memory, projects three service-presence booleans, and sends a fixed diagnostic envelope through `window.postMessage`. The bridge checks source, exact origin, field names/types, serialized size, and a 128-message cap; it constructs a fresh allowlisted object before calling `runtime.sendMessage`. The service worker checks sender extension ID, top-level frame, tab ID, exact origin and `/game/` path, payload keys/types, and size. Static inspection found no code to read cookies, headers, request bodies, tokens, local storage, social/chat content, or to upload any data. The probe does not issue its own network requests or gameplay actions.

The local [runtime boundary check](issue-23-chrome-probe/check-runtime.mjs) accepts a valid message and rejects unknown fields, an oversized payload, wrong origin, subframe, wrong extension ID, and missing tab identity. Syntax checks passed for all three scripts. The **live Chrome run** confirmed both `document_start` scripts began while the document was `loading`, one startup/metadata XHR marker reached the runtime, four deliberately malformed or wrong-source window messages were rejected, and one invalid internal runtime message was rejected. The game rendered with the probe active. The owner removed it and reloaded; the diagnostic attribute disappeared. The local tests exercise more sender variants than the one live run. These results support narrow routing, shape, and size controls, **not** source authenticity or production security approval.

A page script can forge a schema-valid message because MAIN shares its world; it can also change the diagnostic DOM attribute. A malicious page could therefore feed plausible but false city booleans through the checked bridge. The runtime currently acknowledges bounded messages but stores nothing and grants no page command. No raw city fields or identifiers crossed the bridge in this experiment. The XHR wrapper changes page-level function identity, reads a full selected response in page memory, and parses up to 6 MB of text; these are performance and compatibility risks, even though the observed page rendered. The event cap can drop later updates. The fixed `pl4` match does not solve multi-world permission consent. The probe is a research artifact only and must not be copied into `apps/extension` as production integration. **Security & Privacy review conclusion:** the experiment stayed within the stated minimization boundary and found no exfiltration path in its source, while authenticity, exact-field projection, permission UX, update loss, and sustained noninterference require design-specific review before release.
